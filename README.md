# 📈 한국투자증권 Open API 기반 모의투자 체결 시스템

## 📌 프로젝트 소개

한국투자증권(KIS) Open API를 활용해 실시간 시세를 받아오고, **외부 증권사에 주문을 위임하지 않고 직접 설계한 매칭 엔진**으로 체결까지 처리하는 모의투자 시스템입니다.

실무에서 경험하기 어려운 세 가지를 이 프로젝트 하나로 직접 체득하는 것을 목표로 잡았습니다.

- **체결 로직 자체 설계**: 실제 거래소의 가격-시간 우선순위(Price-Time Priority) 원칙을 구현하고, 그 위에 자동 가격개선(Price Improvement) 로직을 직접 설계
- **이벤트 기반 비동기 아키텍처**: Kafka로 주문 접수와 체결 처리를 분리, WebSocket/SSE로 시세·체결 결과를 실시간 스트리밍
- **관측 가능한 운영**: FDS 이상거래탐지 + Loki/Grafana 로그 파이프라인 + 어드민 모니터링까지 갖춰 "만들고 끝"이 아니라 "운영 중 문제를 스스로 찾아내는" 구조까지 구현

토큰 발급부터 시세 조회·주문·체결·모니터링까지 실서비스에 가까운 흐름을 설계하고 AWS EC2에 배포해 운영 경험까지 확보했습니다.

```
└── security     # Spring Security 설정
```

## 🔄 핵심 기능 구현 상세

### 1️⃣ 자체 주문 매칭 엔진 — 가격-시간 우선순위 + 자동 가격개선 (핵심 구현)

외부 증권사 API에 주문을 위임하지 않고, 체결 로직의 동작 원리를 구조적으로 이해하기 위해 직접 설계했습니다.

**가격-시간 우선순위 (Price-Time Priority) — 종목별 우선순위 큐(Heap) 기반**
- 실제 연속경쟁매매(continuous double auction) 거래소가 쓰는 원칙을 그대로 구현: 매수는 지정가가 **높을수록**, 매도는 지정가가 **낮을수록**(= 더 공격적인 주문일수록) 먼저 호가를 소진하고, 동일 가격이면 먼저 낸 주문이 우선
- 종목코드별로 매수/매도 `PriorityBlockingQueue`(`OrderBook`)를 메모리에 유지해 삽입 시 O(log n)으로 우선순위를 반영, 매칭 시점엔 DB 재정렬 없이 큐에서 O(log n)에 최우선 주문을 꺼냄 — 큐엔 정렬용 값(주문ID/가격/생성시각)만 담은 불변 스냅샷을 두고, 한 배치 사이클에서 꺼낸 주문들의 최신 DB 상태를 `findAllById`로 한 번에 조회해서 처리(취소/체결된 주문은 이 시점에 자연스럽게 걸러짐 - lazy deletion). 앱 재시작 시엔 DB의 대기 주문으로 큐를 다시 채워서, 메모리 큐는 어디까지나 DB 위에 얹은 성능 최적화 계층으로 동작
- `MatchingService`가 이 순서대로 호가 10단계 잔량을 실제로 차감해가며 여러 주문의 중복 체결을 방지

**자동 가격개선(Price Improvement) 5% 밴드 — 자체 설계 로직**
- 지정가 매수 주문이 그보다 저렴한 매도호가를 만나면 자동으로 더 유리한 가격에 체결시키되, 지정가 대비 **5%를 초과해서 싼 호가는 개선 대상에서 제외**(이상 데이터로부터 보호, 베타 단계 기능 범위 제한 목적으로 자체 설계)
- 현재가(시장가) 매수는 이 밴드 없이 지정가(주문 시점 현재가) 이하 호가면 그대로 체결 — 지정가 전용 기능으로 명확히 분리

**그 외 매칭 엔진 설계**
- **체결 원장(Trade) 분리**: 체결마다 `Trade` 테이블에 INSERT(불변 원장), `Order`는 누적 체결수량/최근체결가/최종상태만 관리 — **JPA/Hibernate**로 객체지향 도메인 모델 설계를 직접 체득하기 위해 의도적으로 선택
- **호가 10단계 기반 실제 부분체결**: 조건에 맞는 호가 잔량만큼만 체결, 모자란 만큼은 다음 주기로 이월. 체결 결과(`FillPlan`)처럼 한 번 계산되면 바뀌지 않는 값은 **Java 21 record**로 표현해 불변성을 코드로 보장
- **주문 상태 머신**: `PENDING` → `PARTIAL` → `MATCHED` / `CANCELLED`
- **주문 생성 시점 잔고/보유수량 예약(reservation)**: 매수는 주문 즉시 예상 금액만큼 잔고 선차감(부족 시 주문 자체 거부), 매도는 보유수량 검증. 취소 시 미체결분 환급, 실제 체결가가 지정가보다 유리했으면 차액도 자동 환급 — 잔고 변경과 주문 상태 저장은 `@Transactional`로 묶어서, 처리 도중 예외가 나도 "잔고만 변하고 주문 기록은 안 남는" 반쪽짜리 상태가 생기지 않도록 함
- **Kafka 기반 비동기 처리**: 주문 요청 → Kafka Topic 발행 → `MatchingService` 소비, 즉시 1차 체결 시도 후 실패하면 30초 배치로 재시도. **Kafka**를 선택한 이유는 주문 접수(빠른 응답이 중요)와 체결 처리(무거운 매칭 로직)의 관심사를 분리해, 매칭이 지연되더라도 주문 API 응답 자체는 막히지 않게 하기 위함

### 2️⃣ FDS(이상거래탐지) — 규칙 기반 실시간 탐지

거래 시스템의 신뢰성을 위해, 매칭 엔진과 별도로 세 가지 규칙 기반 패턴을 실시간 탐지하는 모듈을 직접 설계했습니다.

| 규칙 | 조건(기본값) | 탐지 시점 |
|---|---|---|
| 과다 주문 빈도 | 60초 내 10회 이상 주문 | 주문 제출 시 |
| 초단타 왕복매매 | 60초 내 같은 종목 반대매매 | 체결 시 |
| 가격 이상치 | 지정가가 현재가 대비 20% 이상 이탈 | 주문 제출 시 |

- **차단하지 않고 관찰만 함** — 오탐이 정상 거래를 막지 않도록, 탐지되면 로그(Loki)에 남기고 어드민 화면에 SSE로 실시간 알림만 전송하는 것으로 설계 범위를 명확히 한정
- 회원별 슬라이딩 윈도우(`Deque<LocalDateTime>`)로 주문 빈도를 추적, 별도 배치 없이 요청 시점에 바로 판정 — 규칙 3종 수준에서는 Kafka Streams 같은 별도 스트림 프로세싱 프레임워크 없이 순수 Java 컬렉션(`ConcurrentHashMap` + `Deque`)만으로 충분하다고 판단해 의도적으로 가볍게 구현

### 3️⃣ 실시간 주식 시세 — KIS 웹소켓 구독 최적화

- **거래량 상위 종목 랭킹**: 정규장(09:00~15:30) 동안 REST로 폴링, 그 외 시간엔 캐싱된 마지막(종가) 데이터를 재사용. REST 호출은 **WebClient**로 처리해 톰캣 스레드를 블로킹하지 않도록 함
- **개별 종목 호가 10단계**: **KIS 실시간 웹소켓**(H0STASP0) 단일 채널만 구독. REST 폴링은 폴링 주기만큼 구조적으로 지연이 생기는데, 밀리초 단위로 반영하기 위해 웹소켓을 도입 — 애초에 매칭 엔진도 호가만 사용하고, 화면에 필요한 현재가/등락률/전일대비도 호가 최우선단계 중간값 + 전일종가로 계산 가능해서 **종목당 실시간 등록을 2건(체결가+호가)에서 1건으로 50% 절감**, 세션 등록 한도 내에서 동시 지원 가능한 종목 수를 확대
- 누적거래량만 호가 프레임에 없는 값이라 REST로 30초마다 별도 보충
- **SSE**로 브라우저에 실시간 스트리밍(랭킹/현재가·호가/보유종목 각각 독립 스트림) — 서버→브라우저 단방향 전달에는 WebSocket보다 가벼운 HTTP 기반 SSE로 충분하고, 재연결도 브라우저가 알아서 처리해줘서 선택

### 4️⃣ AI 뉴스 영향 분석

- 종목 상세페이지에서 관련 뉴스(네이버 뉴스 검색 API)를 최근 1일 기준 수집, **Anthropic Claude API**에 구조화 출력(structured output)으로 전달해 "오늘 등락이 이 뉴스들과 유의미하게 관련 있는지, 방향(상승/하락)과 근거"를 분석 — LLM 응답을 자유 텍스트로 받아 직접 파싱하는 대신, 구조화 출력으로 바로 타입이 있는 객체를 받아 화면에 꽂아 쓰기 위해 Claude를 선택
- LLM이 "유의미하지 않음"으로 판단하면 억지로 보여주지 않고 "분석 중" 상태로 남겨 노이즈 방지
- 종목·날짜 단위로 캐싱(하루 한 번만 호출) — 같은 종목을 여러 번 봐도 API를 반복 호출하지 않음(비용/응답속도 모두 고려)

### 5️⃣ `@Scheduled` 기반 재시도 & 장마감 자동취소

- 30초 주기 스케줄러(Spring `@Scheduled`)로 `PENDING`/`PARTIAL` 상태 주문을 호가 기준으로 재매칭, 주문 접수는 오전 8시부터 가능(대기)하되 실제 체결은 정규장(09:00~15:30)에만 수행 — 재시도 작업 하나뿐이라 Spring Batch 같은 무거운 배치 프레임워크 대신 단순 스케줄러로 충분하다고 판단
- **장마감 자동취소**: 정규장 종료 시점까지 남은 미체결 주문은 하루 한 번 일괄 취소(매수는 예약 잔고 자동 환급)
- 미체결 사유(호가 데이터 없음/체결 가능 호가 없음/시스템 오류)를 주문에 기록해 어드민 화면에서 추적 가능

### 6️⃣ 어드민 모니터링 / 관측 인프라

- `/admin/orders`: 미체결(`PENDING`/`PARTIAL`) 주문과 미체결 사유를 한눈에 조회, 주문별 로그 원본을 Loki에서 바로 확인(Grafana 없이도 조회 가능)
- FDS 탐지 결과·매칭 중 예외를 SSE로 실시간 푸시하는 관리자 알림 스트림
- 접근 제어는 별도 권한(Role) 체계 없이 로그인한 회원 ID를 `admin.member-id` 설정값과 비교하는 방식(단일 관리자 계정 전제)
- 로컬 로그 파이프라인: `observability/docker-compose.yml`로 **Grafana Loki + Grafana**를 띄우고, 앱이 Logback 어펜더로 로그를 Loki에 직접 전송(Promtail 같은 별도 로그 수집기 없음) — 정형 로그를 시계열로 검색/조회하는 데 필요한 만큼만 가볍게 구성

### 7️⃣ 회원 관리
- **Spring Security** 기반 폼 로그인 + **카카오 소셜 로그인**(최초 로그인 시 자동 회원가입) — 표준 보안 프레임워크에 OAuth2 Client가 내장돼 있어 커스텀 인증 필터 없이 카카오 로그인을 붙일 수 있었고, 국내 서비스 특성상 가장 보편적인 소셜 로그인 수단이라 카카오를 선택
- 가입 시 초기 투자금 10,000,000원 지급
- **마이페이지**: 닉네임/전화번호 수정, 회원 탈퇴(탈퇴 계정은 재로그인 차단), 보유 종목·거래내역·**이번달 매매차익(기간별 그래프)** 실시간 조회

### 8️⃣ 보안
- KIS/네이버/카카오/Anthropic API 키를 코드에서 완전히 분리 — 환경변수 또는 gitignore 처리된 로컬 시크릿 파일(`application-secret.yaml`)로만 주입
- DB는 별도 서버 없이 단일 파일로 운영 가능한 **H2(File Mode)**를 선택 — 소규모 개인 프로젝트 배포 규모에 맞춘 실용적 선택

## 🔗 주문 처리 흐름

```
[1] 주문 요청 (매수/매도, 현재가/지정가)
   ↓
[2] 잔고(매수)/보유수량(매도) 검증 후 즉시 예약(차감) - 부족하면 주문 자체 거부
   ↓
[3] FDS 1차 검사(주문 빈도/가격 이상치) - 이상 감지 시에도 차단은 안 하고 알림만
   ↓
[4] Kafka Topic 발행
   ↓
[5] MatchingService가 가격-시간 우선순위로 정렬된 순서대로, 실시간 호가 10단계 기준 체결 가능 수량만큼 매칭
   ↓
[6] 체결분은 Trade 테이블에 INSERT, Order는 누적 상태 갱신 (PENDING → PARTIAL → MATCHED), FDS 2차 검사(왕복매매)
   ↓
[7] SSE로 실시간 체결 결과 전달 (보유종목/거래내역/매매차익도 함께 갱신)
   ↓
[8] 미체결 잔량은 PARTIAL 상태로 대기 → 30초 배치로 재시도, 장마감까지 미체결이면 자동취소 (또는 사용자가 직접 취소)
```

## 🚀 배포

- AWS EC2 (Ubuntu) — 단일 인스턴스에서 Kafka/Zookeeper와 앱을 함께 구동
- 로컬에서 `./gradlew clean build` → `build/libs/stockTrade-0.0.1-SNAPSHOT.jar` 를 SCP로 전송
- 서버에서 기존 프로세스 종료 후 `SPRING_PROFILES_ACTIVE=prod nohup java -jar stockTrade-0.0.1-SNAPSHOT.jar &` 로 재기동
  - **`prod` 프로파일 필수**: 기본 `application.yaml` 은 정적 리소스/템플릿 경로를 `file:src/main/resources/...`(개발용 파일 경로)로 잡고 있어, 프로파일 없이 JAR로 띄우면 CSS/JS가 404 → 로그인 리다이렉트로 이어져 화면이 깨진다. `application-prod.yml` 이 이 경로를 `classpath:` 로 되돌린다
  - JAR 파일만 덮어쓰고 재기동을 빠뜨리면 실행 중인 JVM은 옛 파일을 계속 물고 있으므로, 배포 시 반드시 프로세스를 내렸다 올린다 (기존 프로세스가 SSE 연결 때문에 graceful shutdown에 최대 30초 걸리므로, 그 전에 새로 띄우면 8080 포트 충돌로 기동 실패)
- 시크릿(`application-secret.yaml`)은 JAR와 같은 디렉토리에 두거나 환경변수로 주입 — `spring.config.import` 가 실행 디렉토리 기준 상대경로(`./application-secret.yaml`)라, 기동 시 `cd` 한 위치에 파일이 있어야 읽힌다

## ⚠️ 주의사항

- Access Token 만료 시 재발급 필요 (24h), 실시간 웹소켓 승인키도 동일하게 관리
- 요청 헤더 필수 값: `Authorization`, `appkey`, `appsecret`, `tr_id`
- 네이버 뉴스 API 사용을 위해 Client ID 및 Client Secret 키 필요, 카카오 로그인 사용을 위해 카카오 REST API 키/Client Secret 필요, AI 뉴스 영향 분석 사용을 위해 Anthropic API 키 **및 계정 크레딧 잔액** 필요(키/잔액이 없으면 분석은 예외 없이 조용히 "분석 중" 상태로 폴백됨)
- 어드민 화면(`/admin/orders`)과 로그 조회를 쓰려면 `observability/docker-compose.yml`로 Loki+Grafana를 로컬에 띄워야 함(`docker compose up -d`)
- **모든 API 키는 코드에 직접 넣지 않고, 환경변수 또는 프로젝트 루트의 `application-secret.yaml`(gitignore 처리됨, `application-secret.yaml.example` 참고)로 주입**
