# 📈 한국투자증권 Open API 기반 모의투자 체결 시스템

## 📌 프로젝트 소개

한국투자증권(KIS) Open API를 활용해 실시간 시세를 받아오고, **외부 증권사에 주문을 위임하지 않고 직접 설계한 매칭 엔진**으로 체결까지 처리하는 모의투자 시스템입니다.

실무에서 경험하기 어려운 세 가지를 이 프로젝트 하나로 직접 체득하는 것을 목표로 잡았습니다.

- **체결 로직 자체 설계**: 실제 거래소의 가격-시간 우선순위(Price-Time Priority) 원칙을 구현하고, 그 위에 자동 가격개선(Price Improvement) 로직을 직접 설계
- **이벤트 기반 비동기 아키텍처**: Kafka로 주문 접수와 체결 처리를 분리, WebSocket/SSE로 시세·체결 결과를 실시간 스트리밍
- **관측 가능한 운영**: FDS 이상거래탐지 + Loki/Grafana 로그 파이프라인 + 어드민 모니터링까지 갖춰 "만들고 끝"이 아니라 "운영 중 문제를 스스로 찾아내는" 구조까지 구현

토큰 발급부터 시세 조회·주문·체결·모니터링까지 실서비스에 가까운 흐름을 설계하고 AWS EC2에 배포해 운영 경험까지 확보했습니다.

## 🛠 기술 스택 & 도입 이유

| 분류 | 기술 | 왜 썼는가 |
|---|---|---|
| Language | Java 21 | 최신 LTS. record(불변 값 객체)·패턴 매칭으로 체결 결과(`FillPlan`)/캐시 스냅샷(`DailyStats`) 같은 불변 데이터를 간결하게 표현 |
| Framework | Spring Boot, Spring Security (OAuth2 Client) | 표준 웹 스택 + OAuth2 Client 내장으로 카카오 소셜 로그인을 커스텀 필터 없이 연동 |
| ORM | JPA / Hibernate | 실무에서 못 써본 객체지향 ORM 설계를 직접 체득하기 위해 의도적으로 선택 |
| Message Queue | Apache Kafka | 주문 접수(빠른 응답)와 체결 처리(무거운 매칭 로직)를 분리해, 매칭이 오래 걸려도 주문 API 응답이 막히지 않도록 |
| HTTP 통신 | WebClient (비동기) | KIS REST 호출이 톰캣 스레드를 블로킹하지 않도록 리액티브/논블로킹으로 처리 |
| 실시간 통신 | WebSocket (KIS 실시간 호가 수신) | REST 폴링은 폴링 주기만큼 구조적으로 지연이 생김 — 밀리초 단위 반영을 위해 KIS 실시간 채널로 전환 |
| 실시간 통신 | SSE (브라우저 스트리밍) | 서버→브라우저 단방향 전달에는 WebSocket보다 가벼운 HTTP 기반 SSE가 충분하고, 자동 재연결도 브라우저가 처리 |
| AI | Anthropic Claude API | 뉴스 텍스트를 사람이 다시 파싱할 필요 없이 구조화 출력(방향/근거)으로 바로 받아 화면에 꽂아 쓰기 위함 |
| 소셜 로그인 | Kakao OAuth2 | 국내 서비스 특성상 가장 보편적인 소셜 로그인 수단 |
| Database | H2 (File Mode) | 별도 DB 서버 없이 단일 파일로 운영 가능한 경량 구성 (소규모 배포에 적합) |
| 로그/관측 | Grafana Loki + Grafana | 정형 로그를 시계열로 검색하기 위해 도입. Promtail 같은 별도 수집기 없이 Logback 어펜더로 앱이 직접 전송하는 경량 구성 |
| Infra | AWS EC2 (Ubuntu) | 실제 배포/운영 경험 확보 목적 |
| Build | Gradle | - |

## 📂 프로젝트 구조

```
src/main/java
├── token        # 토큰 발급 및 관리 (REST 액세스 토큰 + 웹소켓 승인키)
├── kis          # 한국투자증권 API 연동 (랭킹 REST 폴링 + 실시간 웹소켓)
├── stock        # 주식 시세 조회, 장마감 랭킹 스냅샷 저장
├── order        # 주문/체결/취소, 매매차익 조회
├── matching     # 주문 매칭 엔진 (호가 기반 체결, 가격-시간 우선순위)
├── member       # 회원 관리 (폼 로그인/카카오 소셜 로그인)
├── news         # 관련 뉴스 조회 + Claude 기반 종목 영향 분석
├── fds          # 이상거래탐지(Fraud Detection) - 주문빈도/왕복매매/가격이상치
├── admin        # 미체결 주문 모니터링, Loki 로그 조회, 실시간 알림
├── view         # Thymeleaf 페이지 라우팅
└── security     # Spring Security 설정
```

## 🔄 핵심 기능 구현 상세

### 1️⃣ 자체 주문 매칭 엔진 — 가격-시간 우선순위 + 자동 가격개선 (핵심 구현)

외부 증권사 API에 주문을 위임하지 않고, 체결 로직의 동작 원리를 구조적으로 이해하기 위해 직접 설계했습니다.

**가격-시간 우선순위 (Price-Time Priority)**
- 실제 연속경쟁매매(continuous double auction) 거래소가 쓰는 원칙을 그대로 구현: 매수는 지정가가 **높을수록**, 매도는 지정가가 **낮을수록**(= 더 공격적인 주문일수록) 먼저 호가를 소진하고, 동일 가격이면 먼저 낸 주문이 우선
- `OrderRepository.findPendingBuyOrders`(`price DESC, createdAt ASC`) / `findPendingSellOrders`(`price ASC, createdAt ASC`)로 정렬해 매칭 순서를 결정, `MatchingService`가 이 순서대로 호가 10단계 잔량을 실제로 차감해가며 여러 주문의 중복 체결을 방지

**자동 가격개선(Price Improvement) 5% 밴드 — 자체 설계 로직**
- 지정가 매수 주문이 그보다 저렴한 매도호가를 만나면 자동으로 더 유리한 가격에 체결시키되, 지정가 대비 **5%를 초과해서 싼 호가는 개선 대상에서 제외**(이상 데이터로부터 보호, 베타 단계 기능 범위 제한 목적으로 자체 설계)
- 현재가(시장가) 매수는 이 밴드 없이 지정가(주문 시점 현재가) 이하 호가면 그대로 체결 — 지정가 전용 기능으로 명확히 분리

**그 외 매칭 엔진 설계**
- **체결 원장(Trade) 분리**: 체결마다 `Trade` 테이블에 INSERT(불변 원장), `Order`는 누적 체결수량/최근체결가/최종상태만 관리
- **호가 10단계 기반 실제 부분체결**: 조건에 맞는 호가 잔량만큼만 체결, 모자란 만큼은 다음 주기로 이월
- **주문 상태 머신**: `PENDING` → `PARTIAL` → `MATCHED` / `CANCELLED`
- **주문 생성 시점 잔고/보유수량 예약(reservation)**: 매수는 주문 즉시 예상 금액만큼 잔고 선차감(부족 시 주문 자체 거부), 매도는 보유수량 검증. 취소 시 미체결분 환급, 실제 체결가가 지정가보다 유리했으면 차액도 자동 환급
- **Kafka 기반 비동기 처리**: 주문 요청 → Kafka Topic 발행 → `MatchingService` 소비, 즉시 1차 체결 시도 후 실패하면 30초 배치로 재시도

### 2️⃣ FDS(이상거래탐지) — 규칙 기반 실시간 탐지

거래 시스템의 신뢰성을 위해, 매칭 엔진과 별도로 세 가지 규칙 기반 패턴을 실시간 탐지하는 모듈을 직접 설계했습니다.

| 규칙 | 조건(기본값) | 탐지 시점 |
|---|---|---|
| 과다 주문 빈도 | 60초 내 10회 이상 주문 | 주문 제출 시 |
| 초단타 왕복매매 | 60초 내 같은 종목 반대매매 | 체결 시 |
| 가격 이상치 | 지정가가 현재가 대비 20% 이상 이탈 | 주문 제출 시 |

- **차단하지 않고 관찰만 함** — 오탐이 정상 거래를 막지 않도록, 탐지되면 로그(Loki)에 남기고 어드민 화면에 SSE로 실시간 알림만 전송하는 것으로 설계 범위를 명확히 한정
- 회원별 슬라이딩 윈도우(`Deque<LocalDateTime>`)로 주문 빈도를 추적, 별도 배치 없이 요청 시점에 바로 판정

### 3️⃣ 실시간 주식 시세 — KIS 웹소켓 구독 최적화

- **거래량 상위 종목 랭킹**: 정규장(09:00~15:30) 동안 REST로 폴링, 그 외 시간엔 캐싱된 마지막(종가) 데이터를 재사용
- **개별 종목 호가 10단계**: KIS 실시간 웹소켓(H0STASP0) **단일 채널만** 구독 — 애초에 매칭 엔진도 호가만 사용하고, 화면에 필요한 현재가/등락률/전일대비도 호가 최우선단계 중간값 + 전일종가로 계산 가능해서 **종목당 실시간 등록을 2건(체결가+호가)에서 1건으로 50% 절감**, 세션 등록 한도 내에서 동시 지원 가능한 종목 수를 확대
- 누적거래량만 호가 프레임에 없는 값이라 REST로 30초마다 별도 보충
- SSE로 브라우저에 실시간 스트리밍(랭킹/현재가·호가/보유종목 각각 독립 스트림)

### 4️⃣ AI 뉴스 영향 분석

- 종목 상세페이지에서 관련 뉴스(네이버 뉴스 검색 API)를 최근 1일 기준 수집, **Anthropic Claude**에 구조화 출력(structured output)으로 전달해 "오늘 등락이 이 뉴스들과 유의미하게 관련 있는지, 방향(상승/하락)과 근거"를 분석
- LLM이 "유의미하지 않음"으로 판단하면 억지로 보여주지 않고 "분석 중" 상태로 남겨 노이즈 방지
- 종목·날짜 단위로 캐싱(하루 한 번만 호출) — 같은 종목을 여러 번 봐도 API를 반복 호출하지 않음

### 5️⃣ `@Scheduled` 기반 재시도 & 장마감 자동취소

- 30초 주기 스케줄러로 `PENDING`/`PARTIAL` 상태 주문을 호가 기준으로 재매칭, 주문 접수는 오전 8시부터 가능(대기)하되 실제 체결은 정규장(09:00~15:30)에만 수행
- **장마감 자동취소**: 정규장 종료 시점까지 남은 미체결 주문은 하루 한 번 일괄 취소(매수는 예약 잔고 자동 환급)
- 미체결 사유(호가 데이터 없음/체결 가능 호가 없음/시스템 오류)를 주문에 기록해 어드민 화면에서 추적 가능

### 6️⃣ 어드민 모니터링 / 관측 인프라

- `/admin/orders`: 미체결(`PENDING`/`PARTIAL`) 주문과 미체결 사유를 한눈에 조회, 주문별 로그 원본을 Loki에서 바로 확인(Grafana 없이도 조회 가능)
- FDS 탐지 결과·매칭 중 예외를 SSE로 실시간 푸시하는 관리자 알림 스트림
- 접근 제어는 별도 권한(Role) 체계 없이 로그인한 회원 ID를 `admin.member-id` 설정값과 비교하는 방식(단일 관리자 계정 전제)
- 로컬 로그 파이프라인: `observability/docker-compose.yml`로 Loki + Grafana를 띄우고, 앱이 Logback 어펜더로 로그를 Loki에 직접 전송(별도 수집기 없음)

### 7️⃣ 회원 관리
- Spring Security 기반 폼 로그인 + **카카오 소셜 로그인**(최초 로그인 시 자동 회원가입)
- 가입 시 초기 투자금 10,000,000원 지급
- **마이페이지**: 닉네임/전화번호 수정, 회원 탈퇴(탈퇴 계정은 재로그인 차단), 보유 종목·거래내역·**이번달 매매차익(기간별 그래프)** 실시간 조회

### 8️⃣ 보안
- KIS/네이버/카카오/Anthropic API 키를 코드에서 완전히 분리 — 환경변수 또는 gitignore 처리된 로컬 시크릿 파일(`application-secret.yaml`)로만 주입

## 🔗 주문 처리 흐름

```
[1] 주문 요청 (매수/매도, 현재가/지정가)
   ↓
[2] 잔고(매수)/보유수량(매도) 검증 후 즉시 예약(차감) - 부족하면 주문 자체 거부
   ↓
[3] FDS 1차 검사(주문 빈도/가격 이상치) - 이상 감지 시에도 차단은 안 하고 알림만
   ↓
[4] Kafka Topic 발행
   ↓
[5] MatchingService가 가격-시간 우선순위로 정렬된 순서대로, 실시간 호가 10단계 기준 체결 가능 수량만큼 매칭
   ↓
[6] 체결분은 Trade 테이블에 INSERT, Order는 누적 상태 갱신 (PENDING → PARTIAL → MATCHED), FDS 2차 검사(왕복매매)
   ↓
[7] SSE로 실시간 체결 결과 전달 (보유종목/거래내역/매매차익도 함께 갱신)
   ↓
[8] 미체결 잔량은 PARTIAL 상태로 대기 → 30초 배치로 재시도, 장마감까지 미체결이면 자동취소 (또는 사용자가 직접 취소)
```

## 📌 트러블슈팅 (문제 · 원인 · 해결 · 성과)

| 문제 | 원인 | 해결 | 성과 |
|---|---|---|---|
| **랭킹 캐시가 시간이 지날수록 계속 불어나 화면이 10~20초씩 느려짐** | 앱 재시작 시 랭킹 캐시를 복원하는 쿼리에 날짜 필터가 없어, DB에 쌓인 **모든 날짜**의 EOD 스냅샷을 통째로 읽어와 누적(캐시 초기화 로직도 없음) | 최신 날짜 스냅샷만 정확히 골라오는 쿼리로 교체, 캐시 채우기 전 방어적 초기화 추가 | **(실측)** 랭킹 캐시 15,540건 → **30건**, 메인화면 DOM 노드 264,259개 → **589개(99.8%↓)**, `<tr>` 행 15,540개 → **31개** |
| 서버 기동 후 일정 개수 이상 종목을 보면 신규 종목이 영구 미체결 | 종목당 실시간 채널 2개(체결가+호가) 구독 + 구독 한도 초과 종목에 대한 REST 폴백 경로 부재(호가는 REST 조회 자체가 없음) | 체결가 구독 제거, 호가 단일 채널만 구독 — 현재가/등락률은 호가+전일종가로 계산해 대체 | 종목당 실시간 등록 **2건 → 1건(50%↓)**, 세션 한도 내 동시 지원 가능 종목 수 확대 |
| 대기 주문 매칭이 지정가와 무관하게 접수 순서로만 처리됨 | 매칭 대상 조회 쿼리가 `createdAt` 시간순으로만 정렬(가격 정렬 없음) | 매수는 지정가 높은 순, 매도는 지정가 낮은 순으로 우선 정렬 후 동일 가격은 시간순 재정렬 | 실제 거래소 원칙(가격-시간 우선순위)과 일치하는 체결 정합성 확보 |
| 웹소켓이 "message too big"(1009)으로 끊김 | 여러 종목 동시 구독 시 기본 텍스트 메시지 버퍼(8KB) 초과 | `WebSocketContainer` 버퍼 크기를 1MB로 확대 | 버퍼 **8KB → 1MB(128배)**, 다종목 동시구독 시 연결 끊김 제거 |
| 보유주식 실시간 스트림이 DB 커넥션 풀을 고갈시킴 | 가격 틱마다(초당) 캐싱 없이 DB 재조회 | 회원 단위 **1.5초 TTL 캐시** 추가, 실제 체결 시에만 즉시 무효화 | 반복 조회 시 DB 쿼리 스킵, 커넥션 풀 고갈 재발 방지 |
| 종목 상세페이지 새로고침 시 실시간 데이터가 영영 안 뜸 | SSE 재접속마다 캐시 Sink를 삭제 + 이미 구독된 종목은 웜업 재조회를 안 하는 구조라, 새 틱이 없는 시간엔 재접속해도 빈 화면 | Sink를 연결 종료 시 삭제하지 않고 마지막 값을 재생(replay) | 재접속 시 빈 화면 노출 시간 제거 |
| KIS 초당 호출 제한(EGW00201) 시 재시도 없이 실패 | 기존 재시도 필터가 연결 조기종료만 대상으로 함 | rate-limit 에러도 재시도 대상에 포함, 프론트에도 에러 화면+재시도 버튼 추가 | 일시적 API 제한으로 인한 화면 무한 로딩 제거 |
| SSE 비동기 dispatch 권한 오류 | Spring Security가 ASYNC dispatch 재검사 | `DispatcherType.ASYNC` permitAll 처리 | 인증 필요 SSE 스트림 정상 동작 확보 |
| StaleObjectStateException | String ID에 `@GeneratedValue` 적용 | ID 생성 전략 수동 지정으로 변경 | 주문 저장 시 낙관적 락 충돌 제거 |
| 미체결 주문 체결 안됨 | 매칭 로직이 Kafka Consumer에 혼재 | `MatchingService` 분리 + 30초 배치 재시도 구조로 재설계 | 매칭 로직과 메시지 소비 로직 관심사 분리 |
| 주문 API 인증 누락 | `permitAll` 범위 과도하게 설정 | 주문 엔드포인트 인증 필수로 수정 | 미인증 주문 생성 차단 |
| 로그아웃이 동작 안 함 | Spring Security 로그아웃 필터는 POST만 매칭하는데 로그아웃 링크가 GET(`<a>`) | POST 폼으로 교체 | 정상 로그아웃 플로우 확보 |

## ⚠️ 주의사항

- Access Token 만료 시 재발급 필요 (24h), 실시간 웹소켓 승인키도 동일하게 관리
- 요청 헤더 필수 값: `Authorization`, `appkey`, `appsecret`, `tr_id`
- 네이버 뉴스 API 사용을 위해 Client ID 및 Client Secret 키 필요, 카카오 로그인 사용을 위해 카카오 REST API 키/Client Secret 필요, AI 뉴스 영향 분석 사용을 위해 Anthropic API 키 필요
- 어드민 화면(`/admin/orders`)과 로그 조회를 쓰려면 `observability/docker-compose.yml`로 Loki+Grafana를 로컬에 띄워야 함(`docker compose up -d`)
- **모든 API 키는 코드에 직접 넣지 않고, 환경변수 또는 프로젝트 루트의 `application-secret.yaml`(gitignore 처리됨, `application-secret.yaml.example` 참고)로 주입**
