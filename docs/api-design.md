# REST API 설계

전체 스펙은 [openapi.yaml](openapi.yaml) (OpenAPI 3.0, Redocly lint 통과). 여기서는 **어떤 원칙으로 설계했고 무엇을 포기했는지**를 정리한다.

## 1. 기능 ↔ API 한눈에

| 기능 | API | 인증 |
|---|---|---|
| 가입·로그인 | `POST /api/member/join`, `POST /login`(폼), `GET /oauth2/authorization/kakao`, `POST /logout` | 공개 |
| 주문 접수 | `POST /api/order/create` | 세션 |
| 주문 취소 | `POST /api/order/{orderId}/cancel` | 세션 + 본인 주문 |
| 체결 결과 수신 | `GET /api/order/stream` (SSE) | 세션 |
| 주문 내역·보유·손익 | `GET /api/order/history`, `/holding`, `/holding/stream`(SSE), `/realized-pnl`, `/memberStockInfo` | 세션 |
| 시세·랭킹 | `GET /api/volume/cached`, `/api/volume/stream`(SSE), `/api/stock/{code}/cached`, `/stream`(SSE), `/asking/stream`(SSE) | 공개 |
| 뉴스·AI 분석 | `GET /api/news/{name}`, `/api/news/{code}/analysis` | 공개 |
| 운영(어드민) | `GET /api/admin/session-count`, `/dead-letters`, `POST /dead-letters/{id}/replay`, `GET /logs`, `/alerts/stream`(SSE) | 세션 + 관리자 |

## 2. 설계 원칙과 근거

### 주문은 "접수"와 "체결"을 분리한 비동기 API
- `POST /api/order/create`는 **잔고 예약 + 주문 저장 + Outbox 기록까지만 트랜잭션으로 끝내고 바로 `orderId`를 돌려준다.** 체결은 Kafka로 넘어가 그 종목을 맡은 서버가 처리하고, 결과는 `GET /api/order/stream`(SSE)으로 받는다.
- 근거: 체결은 실시간 호가에 따라 즉시·부분·30초 뒤·장 마감 취소 등 결과가 여러 번, 늦게 나올 수 있다. 요청-응답 안에서 기다리게 하면 주문 API 응답이 매칭 지연에 묶인다.
- 대가: 클라이언트는 "접수됨"과 "체결됨"을 따로 처리해야 한다. 응답 코드는 의미상 `202 Accepted`가 맞지만 기존 화면 호환 때문에 `200`을 유지했다(개선 후보).

### 잔고·보유수량 검증은 접수 시점에
- 매수는 접수 시 `지정가 × 수량`을 **예약 차감**하고, 체결 때는 실제 체결가와의 차액만 환급, 취소 때는 미체결분 환급. 그래서 `GET /api/member/info`의 `seed`는 항상 "지금 주문 가능한 금액"이다.
- 같은 회원의 동시 접수는 회원 행 락으로 한 건씩 처리 → 잔고를 넘는 주문이 들어가지 않음(동시 5건 중 2건만 접수되는 것을 통합 테스트로 검증).

### 상태 충돌은 409로 드러낸다
- 취소와 체결이 같은 순간 겹치면 `Order @Version`으로 나중 쪽이 실패한다. 취소가 지면 **환급까지 전부 롤백하고 `409 Conflict`** - 클라이언트는 잠시 후 내역을 다시 보거나 재시도한다.
- 근거: "취소됐다고 응답했는데 실제로는 체결됨"(또는 그 반대)을 만들지 않는 게 우선. 서버가 몰래 재시도하지 않고 결과를 그대로 알린다.

### 리소스 소유권은 경로가 아니라 세션에서
- 회원 ID를 경로·쿼리로 받는 API가 없다. 내역·보유·손익은 모두 세션의 회원 ID로만 조회 → 다른 회원 ID를 넣어 남의 데이터를 보는 경로(IDOR) 자체가 없음.
- 주문 취소처럼 리소스 ID를 받는 경우 본인 주문인지 확인하고, 아니면 **없는 주문과 똑같이 404** - 남의 주문 존재 여부도 알려주지 않음.

### 실시간 데이터는 SSE
- 시세·호가·랭킹·체결 결과·관리자 알림은 서버 → 브라우저 단방향이라 WebSocket 대신 SSE를 선택. HTTP 그대로라 nginx·세션 인증을 그대로 쓰고, 끊기면 브라우저 `EventSource`가 자동 재연결한다.
- 서버 여러 대에서도 동작하도록 이벤트 원천을 Kafka 브로드캐스트로 바꿨다: 체결은 B 서버에서 났는데 사용자 SSE가 A 서버에 붙어 있어도 A가 Kafka에서 받아 전달한다.
- 새로 접속하면 마지막 값을 먼저 보낸다 - 장 마감 후처럼 새 틱이 안 오는 시간에도 빈 화면이 아니라 종가가 바로 보인다.

### KIS 호출을 API 요청과 분리
- 시세 API는 요청마다 KIS를 부르지 않고 캐시(= Kafka로 받은 마지막 값)를 돌려준다. 처음 보는 종목이면 `204 No Content` + 시세 수집기에 구독 요청 → 잠시 뒤 값이 생긴다.
- 근거: KIS 호출 한도·토큰 발급 제한(분당 1회)이 있어, 사용자 요청 수가 KIS 호출 수로 이어지면 안 된다. 부하 테스트(k6)도 이 캐시 API를 쓴다.

### 오류 응답
- 본문은 `{"message": "..."}` 하나로 통일. 상태 코드: 400(검증 실패 - 잔고/보유수량 부족, 이미 처리된 주문), 401(로그인 필요), 403(관리자 아님), 404(없거나 본인 것 아님), 409(동시성 충돌).

## 3. 일부러 하지 않은 것 / 알려진 한계

| 항목 | 현재 | 이유 또는 개선 방향 |
|---|---|---|
| 경로에 동사(`/create`, `/cancel`) | 그대로 | 화면 코드 호환. REST 리소스형이면 `POST /api/orders`, `DELETE /api/orders/{id}`(또는 `POST /api/orders/{id}/cancellation`) |
| API 버전 관리(`/v1`) | 없음 | 클라이언트가 같은 저장소의 화면 하나뿐이라 아직 필요 없음. 외부 공개 시 도입 |
| 주문 내역 페이지네이션 | 없음(전체 반환) | 인덱스로 조회는 빠르지만 응답 크기가 무한정 커짐 → `createdAt` 커서 기반 페이지네이션 필요 |
| 멱등키(`Idempotency-Key`) | 없음 | 네트워크 재시도로 같은 주문이 두 번 접수될 수 있음(잔고 예약은 정확하지만 의도치 않은 중복 주문). 헤더 + 유니크 키 테이블로 도입 후보 |
| CSRF | 비활성화 | 세션 쿠키 인증이라 CSRF 보호가 필요한 구조. 화면이 fetch로 JSON을 보내므로 `SameSite=Lax` 쿠키 + CSRF 토큰 헤더 도입이 다음 단계 |
| 요청 본문을 엔티티(`Order`, `Member`)로 직접 받음 | 그대로 | 서버가 정하는 필드(주문 ID·상태·잔고 등)는 서비스에서 덮어써 막고 있음. 요청 전용 DTO로 분리하는 게 더 안전 |
